# 《学习通知开通步骤（2026-11-03）》可行性评估

评估对象：`通知开通步骤-20261103(1).md`（微信临时目录，只读，未修改）
评估时间：2026-11-03 11:10–11:30
代码基线：`6feb1a2 fix: customize reminders and clarify account privacy`

## 结论

**方案技术上可行，代码主体已经具备；但当前环境不能直接完成真实推送验收，存在 4 个硬缺口：**

1. 当前本机签名 Profile 未见 Push Kit 能力授权（`app-privilege-capabilities` 与 `acls.allowed-acls` 均为空）；
2. 没有 AppGallery Connect 的项目 ID；
3. 没有服务账号 JWT 文件与私钥，也没有自动续期机制；
4. 没有带 Push 能力的真机签名包和真实手机，无法做送达/点击验收。

文档对“代码已实现什么、还缺什么”的描述与仓库基本一致，可以作为开发团队的开通操作手册；但必须补齐
AGC 开通、重新申请 Profile、重签 HAP、配置 JWT 与真机验收，不能只改 `.env`。

当前 HAP 的 Profile 与 debug p7b 逐字节一致（SHA-256 `c91953e0…f099`）。这意味着：

- 当前 HAP 能安装、能启动、能使用应用内提醒；
- 但 `pushService.getToken()` 很可能拿不到有效 Token，或平台拒绝推送；
- 按文档第 1.4 条，必须在 AGC 开通 Push Kit 后重新申请调试/发布 Profile 并重新签名。

> 不能把“能安装的 HAP”当作“具备 Push 能力的 HAP”。这是文档里已经提醒、但当前本地材料确实不满足的一项。

## 建议的落地顺序

1. **先开通再重签**：AGC → 增长 → 推送服务 → 开通；记录项目 ID；申请场景化消息分类；重新申请 debug Profile；用新 Profile 重签 HAP。
2. **准备服务账号**：创建服务账号、授权 Push Kit、生成私钥；用官方示例生成 JWT，放入 `E:/private/push.jwt`（或容器 `/run/secrets/push.jwt`），不要入库。
3. **配置后端**：在 API 与 Worker 共用环境写入 `HUAWEI_PUSH_PROJECT_ID`、`HUAWEI_PUSH_JWT_FILE`、`HUAWEI_PUSH_CATEGORY`；重启 API 与 `reminder_worker.py`。
4. **设备验收**：真实手机登录 → 允许通知 → 确认 `/api/v1/reminder-devices` 返回 `active=true`、`hasToken=true`、`permission=true` → 设置提醒时间/免打扰 → 杀后台等待 Worker 扫描 → 验证收到与点击。
5. **补运维**：JWT 到期前原子替换；补平台错误码映射、送达/点击回执、通知直达任务详情。

## 总结

这份步骤文档是**可执行的**，代码也已完成大部分；但“开通 Push Kit”不是纯本地配置，涉及 AGC 账号、
Profile 重签、服务账号 JWT、已获准 category 和真实手机。当前仓库可以直接做的是：准备环境变量、启动 Worker、
维护应用内提醒；不能直接做的是：用现有 HAP 完成真实推送送达。建议先完成 AGC 开通与重签，再按文档第 4 步验收。

## 如果确实要补这两项能力

### 先看这张截图：为什么“系统权限已开”仍提示不可用

截图里的三行分别是：

- 系统通知权限：已开启 → 手机侧允许通知，没问题；
- 后台提醒服务尚未接通 → 服务端 Push Kit 未配置（`pushConfigured=false`），不是系统权限问题；
- 应用关闭后暂时收不到通知 → 当前没有可用的后台发送通道。

**这不是“代理提醒没开”造成的。** 当前代码的提醒通道是 Push Kit；代理提醒是另一套本机定时机制。
只去 AGC 点“代理提醒”，这张截图不会变成“可用”，因为客户端没有调用 `reminderAgentManager`。
要么按通知文档把 Push Kit 配通，要么改客户端走代理提醒；两条路选一条，不要指望一个 AGC 开关解决。

### A. 代理提醒（本机定时，不是 Push Kit）

- **AGC**：开放能力管理 → 代理提醒 → 申请，说明提醒用途和场景。
- **客户端代码**：新增 `@ohos.reminderAgentManager` 服务；申请 `ohos.permission.PUBLISH_AGENT_REMINDER`；
  用 `ReminderRequestCalendar` / `ReminderRequestAlarm` 发布、更新、取消提醒；处理通知权限和用户关闭开关。
- **限制**：只能本机定时；受系统配额/权限限制；不能替代服务端多设备调度；如果和现有 Push Kit 同时存在，
  必须做去重，否则同一提醒会收到两次。
- **工作量**：中等。新增服务、权限、页面入口、持久化、测试；不建议为了“上架”临时把 Push Kit 换成它。

### B. 锁屏卡片（不是现有桌面服务卡片）

- **AGC**：开放能力管理 → 锁屏卡片 → 申请；锁屏卡片只支持 `1*1` / `1*2`，需说明展示内容。
- **客户端代码**：按华为《锁屏卡片开发指导》新增一个锁屏卡片 Form（`1*1` / `1*2`），
  独立于现有 `LearningCardFormAbility`（`2*2` / `2*4` 桌面卡片）；复用 `LearningCardService` 的数据，
  配置锁屏入口/刷新；锁屏卡片不提供弹窗强提醒，不能替代通知。
- **限制**：尺寸仅 `1*1` / `1*2`；需要真机锁屏验证；上架审核会看实际展示内容。
- **工作量**：中高。新增卡片 UI、form 配置、入口、刷新逻辑、真机验收；不是“勾选一下 AGC”就能出现。

### 结论

- **只上架当前功能**：这两项都不申请；真正要开通的是 Push Kit（以及已配好的华为账号）。
- **要新增这两项功能**：AGC 申请 + 客户端实现 + 重新签名 + 真机验收，缺一不可；只点 AGC 不会生效。

### 推荐路线

**继续用当前 Push Kit 方案**，不要改用代理提醒：

1. AGC 开通「推送服务」，记录项目 ID，申请已获准的 category；
2. 重新申请 Profile → 重签 HAP（当前 Profile 的 `app-privilege-capabilities` 为空，这是硬阻塞）；
3. 创建服务账号 → 生成 JWT → 配 `.env` → 重启 API 与 Worker；
4. 真机登录、授权通知、绑定设备，验证送达与点击；
5. 后续再补 JWT 自动轮换、平台回执、通知直达任务详情。

如果确实想走“代理提醒”而不是服务端 Push，需要改客户端（`reminderAgentManager`）、重新申请代理提醒能力，
并接受“只能本机定时、无多设备/服务端统一调度”的限制；当前代码不是这个架构，不建议临时切换。
