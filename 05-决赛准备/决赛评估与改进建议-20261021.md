# 知学 Mate 决赛评估与改进建议

评估日期：2026-10-21。依据：用户提供的 11 页《2026“中国高校计算机大赛―人工智能创意赛”鸿蒙高校创新赛竞赛规程》，以及当前仓库根目录工作副本。

## 1. 我的判断

保留现有技术栈、签名环境和核心架构，围绕“大学生如何在有限时间内完成最重要的学习任务”继续打磨。

项目已具备自然语言入口、课程与 DDL 导入、错题识别、知识画像、诊断练习、确定性判分、计划变化、执行追踪、学习搭子、桌面卡片与跨设备任务同步代码。这些足以支撑有完整过程的现场演示。

目前最有价值的决赛投入是：修复账号边界和多知识点评估问题，统一学习数据和计划状态，把用户资料贯通到练习与解析，完成可持续的主动提醒和真实设备验证，并拿出真实使用证据。建议暂停扩展新的智能体角色、课程门类和社交功能，集中增强现有闭环。

建议作品核心表述：**知学 Mate 根据课程截止时间与真实学习证据，推荐下一项可执行任务，在练习或学习完成后更新画像和计划，并通过鸿蒙卡片、通知和跨设备能力把任务送到合适的入口。**

其中“学习完成后更新”“跨设备”等承诺，需要按本文列出的边界补齐并实测后再写入最终材料。

| 规程依据 | 明确要求 | 对项目的行动建议 |

规程只明确演示视频≤5分钟，未在本文件中给出现场陈述和问答各自时长。文档写全国总决赛在11月，不能据此推定具体日期或地点。

## 4. 当前值得保留并作为技术亮点展示的部分

1. **核心成绩计算可复核。** `app/tools/assessment_tools.py` 负责确定性判分与更新，模型负责意图理解、内容生成和解释。适合展示同一输入得到可核验输出。
2. **工作流具有实际状态。** `app/runtime/loop.py`、`session.py` 与 `api/workflows.py` 包含状态版本、等待答案、恢复、步数限制和持久化，能说明执行过程如何继续。
3. **存在有用的证据链。** 画像、练习结果、计划版本差异和 trace 已有结构。决赛可以让评委从任务追溯到触发证据，不必只听口头描述。
4. **降级路径已经有意识地区分来源。** 在线与 Fixture 路径、LLM 使用标识、图片识别失败提示、资料解析失败状态都有实现；保留这些设计，但需要统一界面口径。
5. **新账号并非只能体验二叉树。** 课程知识点提取、资料知识点合并、未知知识点现场出题已经实现，应在这些基础上补强适用性。
6. **鸿蒙能力已有工程入口。** 卡片扩展、意图执行器、语音服务、分布式数据对象均有实现。下一步是验证真实设备上的用户过程，而不是继续堆登记项。

架构表述建议准确写为：“五个职责模块配合受控工作流，支持模型决策与确定性回退；结果计算由可测试工具执行。”把 LLM、规则、前端本地能力各自做什么说明白，比笼统宣称全自主多智能体更容易回答追问。

## 5. 第一优先级：真实试用前应修复

### A. 账号隔离与身份认证

**已复现，优先级最高。**

隔离环境中创建甲、乙两个账号后：

| 请求场景 | 当前结果 |
|---|---|
| 使用甲的合法令牌读取乙的 `/api/v1/profile/<乙ID>` | HTTP 200，取得乙画像 |
| 未登录读取乙画像 | HTTP 200 |
| 未登录指定乙的 userId 获取当前计划 | HTTP 200 |
| 使用甲令牌读取乙的 plan diff | HTTP 200 |
| 未登录指定乙的 userId 查询资料库 | HTTP 200，返回乙的资料库 |
| 甲通过创建接口传入乙已有的 sessionId | HTTP 200，返回乙会话标识及状态摘要 |

代码依据：

- [身份解析](../server/zhixue-agent-server/app/api/identity.py#L47) 在未登录时接受任意显式 userId；无效 Bearer 也会失去登录身份并继续走游客路径。
- [画像读取](../server/zhixue-agent-server/app/api/profile.py#L20) 直接按路径 ID 读取。
- [计划变化读取](../server/zhixue-agent-server/app/api/plans.py#L198) 没有归属检查。
- [工作流创建](../server/zhixue-agent-server/app/api/workflows.py#L101) 对已有 sessionId 直接返回，早于所有权校验。

这与旧测试中刻意保留的“读开放”设计有关，**不能说它是本次改坏的回归**。但真实用户的学习画像、错题和资料不应沿用演示数据的公开规则，账号页当前“不会被其他身份读到”的文案也需要与实际行为对齐。

另外，[华为账号登录](../server/zhixue-agent-server/app/auth/service.py#L717) 当前接受客户端提供的 OpenID 并签发本系统会话，未见可信凭据的服务端验证。我用同一个自填 OpenID 连续请求，得到201创建、200登录和同一账号的新会话；这证明当前接口对该标识的信任边界不足，并不证明真实华为授权已被绕过或平台本身存在问题。

**建议实现**：

- 游客仅访问明确的 demo-user 演示数据；真实用户资源必须由有效会话确定身份。
- 无效/过期令牌返回401；跨账号资源统一404或403；各读写接口采用同一所有权规则。
- 画像、资料、计划、trace、工作流、导出快照均列入访问控制矩阵。
- 华为登录在服务端验证授权凭据，再映射本地账号；在这条链路完成前，将该能力状态准确标为待完善。
- 公开试用环境关闭演示重置与全量实验快照，或限制为开发/演示管理操作。

**验收**：甲、乙、游客、失效令牌四种身份，分别覆盖自己的资源、别人的资源、演示资源；换账号后本地卡片、缓存和异步结果也必须归属正确。

### B. 多知识点掌握度被同一个旧分数覆盖

**已通过真实 API 链路复现。**

我在隔离账号中建立知识点A掌握度10、知识点B掌握度90，各提交一道正确题。当前 API 返回200，持久化后的分数变成 **A=39、B=39**。B原本90，却因答对题下降到39。

原因：提交接口先选一个 lead point，取一个 `old_mastery`；[判分工具](../server/zhixue-agent-server/app/tools/assessment_tools.py#L49) 对所有知识点复用这个基数，再把结果写回各知识点。单知识点演示用例不会暴露该问题。

[AssessmentResult.dominant_knowledge_point](../server/zhixue-agent-server/app/domain/assessment.py#L39) 还按正确率从高到低选择代表知识点；如果其用途是决定补弱目标，应重新定义选取规则，避免先选出答得最好的一项。

**建议实现**：按知识点传入 `oldMasteryByPoint`，分别计算并返回前后分数、题量和证据；重排使用当前需要补强的知识点。保留现有确定性判分结构，先修正数据模型，再讨论算法升级。

**验收**：不同初始分数、全部答对/全部答错/混合对错、同一提交重试、重复题、跨知识点题集；未覆盖的知识点分数不变，已掌握的知识点不会借用他人的基数。

### C. 专注成果和完成状态缺少持久化闭环

**静态代码确认的实现缺口，设备行为还需实测。**

[AppState](../app/entry/src/main/ets/data/AppState.ets#L981) 将专注记录存入内存数组，任务完成状态放在内存 Map；[LearningDataStore](../app/entry/src/main/ets/cache/LearningDataStore.ets#L12) 当前只保存课程、DDL 和导入状态。[FocusResult](../app/entry/src/main/ets/pages/FocusResult.ets#L62) 没有调用后端专注提交接口。

因此现有结构不足以保证冷启动后保留专注历史、任务完成度或跨设备读取。界面源码也已经说明，等待后端提供专注结果接口后才能跨端同步。

[FocusTimer](../app/entry/src/main/ets/pages/FocusTimer.ets#L61) 采用每次定时器回调增减1秒；应在锁屏、切后台、进程回收场景中验证计时准确性。

**建议实现**：增加有唯一事件ID的 FocusSession 与任务状态持久化；时间由开始时间、暂停累计时间等事实计算；离线记录先保存、联网后幂等补交。自评“已完成”、计时完成和测验掌握应分别记录，避免把自评直接当作知识掌握的证明。

**验收**：完成任务后杀进程重开、退出再登录、同任务多次专注、切后台后恢复、离线完成后联网同步，记录不丢、不重复计入。

## 6. 第二优先级：最能增强创新性和完备度的三项改进

### D. 让新输入持续影响计划，并且尊重可用时间

**已复现的变化未传播**：新账号先导入“数据结构”，再导入“操作系统”，画像中已增加操作系统知识点，但当前计划任务与第一次导入后完全相同。原因是 [profile_merge.py](../server/zhixue-agent-server/app/tools/profile_merge.py#L38) 只在不存在计划时创建计划。

另外，规划初始任务普遍为30分钟；当前重排主要修改目标任务和另一待办任务，没有完整表达可用时段、课程占用、截止日期与每日总时长的约束。隔离函数复现中，原30+30分钟任务在得分0后变成55+15分钟，总时长由60增至70。此增长是现有代码的明确设计，不是算术错误；但如果用户只有60分钟，就需要重新安排。

**建议实现**：

- 课程/DDL/资料/画像变化生成可追踪事件，触发增量重规划，保留已完成状态。
- 专项任务、导入DDL、聊天确认的任务使用统一ID和状态，明确数据归属及版本。
- 先约束空闲时间和截止日期，再按优先级分配；安排不下时明确“超出10分钟”，允许缩短、延期或取消，不能悄悄加任务。
- 每次变化展示简明原因和前后对比，例如“明天截止的作业提前，图算法移至明晚”；支持撤回或重新确认。

**可作为决赛亮点的验收场景**：评委临时把今晚空闲时间由60分钟改成30分钟，或新增明天截止的DDL；系统输出不同且可执行的计划，并说明舍弃与保留的依据。

### E. 把资料检索接到出题和解释，提供可以点开的依据

资料库已有解析、分块、关键词/标签和语义融合检索。但 [exercise_gen.py](../server/zhixue-agent-server/app/agent/exercise_gen.py#L217) 的生成接口主要输入知识点名字和数量；现有提示词还固定为高校计算机课程。没有看到它把用户资料检索片段作为出题上下文。

这意味着“上传资料后获得知识点”和“按该知识点让模型出题”已经可以连起来，但不能直接宣称“题目严格基于上传讲义”。当前聊天层也未见基于资料检索结果生成带引用答案的完整链路。

**建议实现**：

1. 按当前账号和课程检索相关片段，选取足够支持出题的内容。
2. 给生成模块提供课程、知识点、片段和来源ID；题目、答案解析记录来源。
3. 用户可以点开“来自哪份讲义、哪段内容”；PDF来源最好进一步保留页码，当前文本分块还未完整保留这一定位信息。
4. 检索不足时说明“资料不足，无法生成有依据的题目”，或由用户明确选择通用知识题。
5. 对题干重复、选项重复、答案唯一性、解析与标准答案一致性增加校验和抽样人工复核；结构合法不等于内容正确。
6. 将“未测评”与“掌握度低”分开显示。当前导入知识点用0分、confidence=0初始化，再按低分排序，会让尚未测过的内容看起来已经被诊断为最薄弱。

**建议优先完成的一条决赛演示**：现场上传一份新讲义→选出其中一个知识点→生成带来源的3道题→用户答题→解释引用资料→画像及计划根据结果变化。范围控制在一门主示范课程，另一门课程用来验证通用性。

### F. 让主动提醒具备持续性、可解释性和控制权

当前实现有截止任务、考试临近、学习间隔和专注不打扰等规则，值得保留。

实际入口主要是 [EntryAbility.onBackground](../app/entry/src/main/ets/entryability/EntryAbility.ets#L251) 调用 [ProactiveSurfaceService.refresh](../app/entry/src/main/ets/services/ProactiveSurfaceService.ets#L17)。在本次代码范围内未见可在应用长期关闭后仍保证按时重新判断的完整调度机制；也没有完整的提醒冷却、已处理去重、静默时间和稍后提醒状态。

**建议实现**：

- 根据实际允许的系统执行条件设计提醒调度，并在目标设备上实测；先明确能保证哪些触发条件。
- 以任务与触发原因形成提醒标识，记录上次投递、处理、忽略、稍后提醒；通知ID相同只代表覆盖同一通知，不能替代触发去重。
- 提供“稍后提醒”“今天不提醒”“开始这个任务”，让用户控制打扰。
- 卡片和通知标记数据更新时间，避免昨天的任务长期停留。
- 来源不完整时请求补充信息，例如空闲时间、日期或测评；不要以默认值生成看似个性化的结论。

验收时覆盖：前台、切后台、关闭应用、权限拒绝、断网、任务已完成、重复切换前后台、午夜跨天及勿扰设置。未验证关闭应用后的触发能力时，答辩应准确表述为“基于应用生命周期与已有学习上下文提供提醒”。

## 7. 鸿蒙特性的决赛打磨

### 跨设备：把同一任务展示推进到状态接续

[DistributedStateService](../app/entry/src/main/ets/services/DistributedStateService.ets#L18) 当前共享的核心字段是任务JSON、设备标识、更新时间与 active；未包含完整的计时起点、暂停累计、剩余时间及恢复版本。因此当前能力宜表述为“跨设备任务同步”。

建议补充：账号/配对会话归属、任务ID、状态版本、计时事实、显式接续确认和冲突策略。当前全局固定 sessionId 没有体现应用账号隔离，应按实际系统信任边界验证不同应用账号的同步行为；不能仅凭固定ID就断言任意设备能互通，也不能断言已经做了账号隔离。

另有两处生命周期代码值得先修：首次 `init()` 成功加入会话后，没有像“已有对象”分支那样调用 `flushPendingTask()`；`leave()` 没有完整清空 `sessionReady`、`dataObject` 和对端快照。需覆盖“先开始任务后授权”“离开会话后重新初始化”的可重入测试。

目标演示应是真实手机与平板：手机选任务→平板收到并确认接续→状态更新→断开重连→另一端看到同一事件结果。只有本地 `joined session` 日志不足以证明端到端数据流动。

### 服务卡片与意图

卡片已经具备本地快照和点击拉起流程。优先验证任务完成后刷新、账号切换清理、过期提示、冷启动拉起，以及卡片显示任务与实际进入任务一致。

意图执行器已有“开始专注”“查看今日计划”的注册与页面拉起。需要将真实口令拉起、参数接收与恢复身份的过程连起来验证，记录设备与系统版本；“编译产物包含意图”只能证明注册产物存在。

### 大屏与语音

[DeviceLayout](../app/entry/src/main/ets/utils/DeviceLayout.ets#L86) 的窗口绑定把宽度直接传给以vp命名的断点逻辑；源码注释也明确单位应由调用方保证。这里应核对当前SDK回调的单位、补全必要转换，并实测高密度手机、平板横竖屏、分屏；这项尚未在本轮设备验证。

大屏优先把资料列表/内容、练习/解析或计划/依据做成有意义的并排布局；当前集中限宽是基础，不能自动等同于多设备体验创新。

语音已有录音、在线/离线引擎尝试与错误文案。建议验证授权拒绝、连续录音、页面离开、后台中断等场景；识别出的日期与任务先预览确认，再写回。语音完成一条学习任务比单纯展示语音转文字更有说服力。

| 项目 | 目前观察 | 建议 |
|---|---|---|

| 日期 | 模板含固定2026年7月日期；daysLeft被作为导入字段保存 | 保留原日期，每次展示/决策按当前日期重新计算，区分已过期、今天、未设置 |

| 检索成本 | semantic.rerank 每次检索对查询和候选片段重新编码 | 为文档片段保存模型版本与向量缓存，更新文档时重算，记录响应时间与费用 |
| 数据存储 | JSON与SQLite均有，但部分业务依靠进程内全局锁和多次save | 小规模试用优先明确部署约束；业务原子性使用批量写入/事务，不能只靠切SQLite解决全部竞争问题 |
| 身份与异步 | 多页面有请求版本保护，但并非所有写回统一校验账号 | 请求记录owner和版本；返回时身份已变化则丢弃；缓存以账号和查询参数确定归属 |
| 执行轨迹 | trace/evidence提交ID未完全按用户命名 | 提交生成的trace/evidence标识加入用户或全局唯一ID，避免跨账号同一幂等键覆盖 |
| 权限体验 | 启动阶段会尝试请求分布式权限 | 在用户主动选择跨设备功能时解释并申请，拒绝后保证单设备主流程可完成 |

这些不要求一次重写全工程。保留现有API、ViewModel和仓储分层，围绕当前链路逐项修复；对 AppState 和大页面做小步拆分，避免临近决赛的大规模重构。

## 10. 真实用户与落地证据

当前材料中有大量联调、截图与技术审计。我的本轮检索未找到可据以报告效果的真实用户对照试验结果；不据此推断团队从未做过试用。如你们另有反馈，应合并进决赛证据。

建议开展一轮小样本试用，先明确目标人群，例如“同时面临多门考试与作业DDL的大学生”。可先招募8—12位同学验证可用性，再安排持续一周的真实使用。该规模可用于发现问题，不能当成统计上充分证明学习效果的研究。

建议记录：

- 首次完成“导入→计划→练习→变化”的成功人数和操作时间。
- 任务推荐是否被接受、是否执行、被忽略的原因。
- 日期和讲义识别需要人工修正的比例。
- 新增DDL后是否仍能完成计划；重启是否保留进度。
- 模型成功率、响应时间分布、每次完整流程的调用次数及费用。
- 与自行列清单/现有操作方式比较的耗时，保留任务、参与者人数、原始记录和统计方法。

**不要用系统自身的掌握度加分证明学习效果。** 42→58是规则更新结果；真实效果应以独立测验、任务完成、时间成本或用户反馈支持。

落地计划应回答：谁最先用、每周用几次、为何持续回来、没有同伴时单人是否仍有价值、云端模型费用如何承担。学校班级/课程的小范围验证，比泛泛宣称覆盖全部大学生更可信。搭子功能可作为辅助价值，不必抢占主线演示时间。

## 11. 决赛演示与答辩组织

### 主演示建议

以一个学生的一次真实学习过程贯穿：

1. 输入今天的空闲时间，导入一门课与一项DDL。
2. 上传一份资料或一道新错题，系统提出学习动作并说明依据。
3. 完成一组诊断练习，现场解释评分、证据和画像变化。
4. 改变一个条件（新增DDL或缩短可用时间），系统更新计划并显示差异。
5. 从鸿蒙卡片/通知进入同一任务；设备条件成熟时展示手机与平板接续。
6. 重启后查看同一任务和历史，展示状态确实被保存。

视频可以按此压缩到5分钟以内。现场演示按最终通知安排时长，不把5分钟视频限制直接套用到答辩。在线模型有明显等待时提前展示处理阶段；录屏可作故障备份，并明确说明录制时间和版本。

### PPT建议

整理已有27页材料时，建议形成一份主讲版和附录。主讲围绕用户问题、关键创新、完整过程、鸿蒙价值、验证证据与落地计划组织；页数依现场时长决定，规程没有规定PPT必须多少页。

技术架构、权重公式、API清单、失败恢复、签名与设备验证、测试矩阵放附录，随提问打开。每一项功能宣称都对应代码入口、实测记录或明确边界。

### 应准备的追问

- 与“对话模型+待办清单”的具体差异是什么？用“产生可执行动作并根据结果改变计划”的真实过程回答。
- 模型、规则和各Agent分别做什么？用架构和trace说明责任边界。
- 为什么只有3道题就能更新掌握度？说明估计规则、题量局限与后续校准，避免宣称教学验证。
- 新课程、新讲义能否使用？现场更换输入，展示有来源的题目和不足时的提示。
- 应用关闭后还能提醒吗？按经过验证的系统触发范围回答。
- 跨设备同步了什么？区分任务、计时、账号数据和冲突处理的已实现范围。
- 两个同学是否能读取彼此资料？以隔离验收矩阵和接口测试回答。
- 网络、模型配额或设备权限失败怎么办？展示失败状态、可继续执行的动作和恢复方法。
- 用户收益如何证明？提供独立于内置加分规则的真实试用证据。

## 12. 实施顺序和完成标准

| 顺序 | 工作 | 完成标准 |
|---|---|---|
| 1 | 账号访问边界、可信登录、多知识点评估 | 关键复现不再成立，新回归覆盖甲/乙/游客/失效凭据 |
