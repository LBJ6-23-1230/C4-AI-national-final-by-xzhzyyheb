## 一、团队先统一的目标

保留现有 HarmonyOS / ArkTS 前端、Python 后端、五个 Agent 与受控工作流，集中完成：

> **真实输入能改变计划，学习结果能持续保存，五个 Agent 能围绕同一目标协作，鸿蒙能力能在设备上验证。**

核心用户场景：大学生同时面对作业DDL、考试和待掌握知识点时，系统依据真实资料、学习证据和可用时间，决定下一步做什么，执行后再调整。

决赛的产品表述：**学习秘书协调诊断、规划、练习和评估，把目标转成可执行任务，并根据结果持续调整，再通过鸿蒙卡片、通知与设备入口承接同一任务。**

第一阶段集中一门主示范课程，另一门课程用于验证通用性。学习搭子保留为补充。暂缓增加 Agent 角色、新社交功能和大规模界面重构；不为展示协同而让五个角色每次全部运行。

## 三、目标架构与五个 Agent 的职责

入口统一为：聊天、导入、练习、专注、卡片和通知 → 学习应用服务 → 秘书协调与角色执行 → 受控工具 → 持久化状态及事件 → 前端结果与鸿蒙入口刷新。

保留现有API兼容入口，内部逐步接入公共业务服务。API层负责身份与请求校验；角色负责策略及工作产物；工具负责可复核的计算和操作；业务服务负责提交、事务和事件。

| Agent | 独立职责                    | 主要产物                | 需要交接的情况                |
| ----- | ----------------------- | ------------------- | ---------------------- |
| 学习秘书  | 维护用户目标、协调角色、补充缺失信息、判断停止 | 子任务、依赖、约束、下一动作和汇总   | 信息不足询问用户；根据结果委派下一角色    |
| 学情诊断  | 从错题、资料及评估中判断证据与缺口       | 诊断报告、证据引用、待验证假设     | 证据不足请求短测；新结果到达后复核诊断    |
| 学习规划  | 在空闲时段、DDL、课程占用和进度下分配任务  | 可执行计划、无法安排项、取舍和版本差异 | 约束冲突请秘书补充；学习结果变化后重排    |
| 练习辅导  | 检索资料，按目标组织诊断或补救练习       | 带来源的题组、解析、资料缺口      | 资料不足反馈；题目不合格时有限重试      |
| 学习评估  | 确定性评分，逐知识点更新证据与估计       | 逐点评估、置信信息、补测或重排建议   | 将重排请求交给规划，将原因不明的结果交给诊断 |

模型负责语义理解、诊断假设、内容生成与策略提案。判分、分数更新、时间校验、权限、幂等和状态提交继续由代码完成。角色独立不等于独立进程，也不要求每步调用模型。

必须支持三条真实反馈路径：

1. 诊断证据不足 → 练习短测 → 评估 → 重新诊断。
2. 规划发现时间冲突 → 秘书说明取舍或补充约束 → 重新规划。
3. 评估结果需要调整 → 规划生成变更 → 秘书汇总 → 统一提交计划。

协同的验收依据是实际交接、产物引用和行为变化，不以角色数量、调用次数或对话长度衡量。

### T00 基线、数据模型和联调样例对齐

主责：集成负责人；后端、前端和测试共同参与。

- 保存当前改动，明确开发分支与基线，复用本机环境与签名，不重新申请或替换现有材料。

验收：两份契约一致；前后端对同一请求、成功/等待/失败响应和错误处理理解一致；保留一份可重复启动的基线记录。

## 六、阶段1：修复数据可信度与持久化

### T01 账号边界补验收

主责：后端、前端；测试执行矩阵。

- 新增目标、事件、角色产物、资料引用、trace及设备快照均绑定有效身份。
- 请求记录发起账号与版本，返回时账号已切换则丢弃；缓存按账号分区，登出后清理或使其不可访问。
- 卡片、后台同步、待补交队列、历史与异步写回同样遵守账号归属；甲的离线记录不能用乙的身份补交。
- 保留华为登录未完善状态；若后续接通，服务端验证可信凭据后再签发本地会话。

验收：甲、乙、游客、失效令牌访问自己/他人/演示资源；切换账号时并发请求、卡片与离线队列无串号。公开环境开发工具保持关闭。

### T02 修复逐知识点评估，统一提交服务

主责：后端；前端调整结果展示。

- 每个知识点使用自己的旧分、正确率、有效题量和证据，返回逐点前后变化。未覆盖知识点保持原值。
- 普通练习提交和工作流提交复用同一评估业务服务，统一幂等、证据记录和画像写入。
- 核对代表知识点的用途：补弱决策不能默认选择答得最好的一项；补弱优先级规则明确可复核。
- “未测评”“证据不足”“已有测评”分开表示；真实账号缺画像时不注入二叉树42分演示基线。
- 自评完成、专注时长和测评结果分别保存；不把前两者直接当作掌握度提升证据。

验收：A旧分10、B旧分90的混合题组分别更新，不再都变成39；覆盖全对、全错、混合、未覆盖、重复题、并发重试和跨账号同幂等键。评分可确定性复现，但不承诺答对后在所有估计算法下分数必然上涨。

### T03 统一任务与专注状态持久化

主责：后端、前端。

- 课程、DDL、计划任务使用稳定标识与归属；计划变更保留已完成任务和执行历史，不因重排产生重复任务。
- 专注记录保存开始、暂停、继续、结束等计时事实；剩余时间据事实计算，不只依赖定时器每秒回调。
- 完成事件具有唯一ID；前端先持久化离线队列，联网后按原账号幂等补交，服务端保存权威状态。
- 任务完成与画像更新分开；业务写入与事件记录保持原子性。若当前仓储不支持事务，先增加明确的事务/批量提交能力及恢复机制。
- 旧本地记录迁移只导入能确定归属的数据；无法确定归属的记录保留本地并提示，不静默并入新账号。

验收：杀进程重开、退出重登、锁屏恢复、离线完成后联网、重复点击、多次专注同任务均不丢记录、不重复计入；时间误差按设备测量记录。

## 七、阶段2：落实Agent协作和统一执行链

### T04 建立结构化交接与可恢复执行

主责：后端；前端、测试共同评审。

- 子任务最少包含目标ID、子任务ID、负责角色、目标、依赖、输入引用、约束、预期产物和输入版本。区分“Agent子任务”与“用户学习任务”，字段命名避免混淆。
- 角色结果最少包含状态、产物引用、证据ID、简短依据、下一交接请求、实际工具记录和模型/规则来源。
- 状态覆盖完成、等待用户、证据不足、约束冲突和工具失败。运行时验证交接权限、依赖、参数与输入版本。
- 沿用现有步数上限，增加模型调用、重试和总耗时预算；相同证据下重复执行相同动作时停止并说明缺口。
- 保存等待原因和恢复点；模型超时或服务重启后可以继续。旧版本结果不得覆盖用户新修改。
- 标准答案仅供服务端评估工具读取；公共上下文、工作流响应和客户端轨迹不包含答案键。

验收：三条反馈路径均有真实执行记录；有证据账号与无证据账号走不同路径；失败可恢复且不重复提交；轨迹能对应真实产物与版本。

### T05 统一聊天、评估和规划入口

主责：后端；前端接线。

- 聊天识别需求后建立或继续同一学习目标，返回可操作的下一动作；前端从聊天进入计划、练习和轨迹时保留上下文。
- 将画像、任务、评估和计划写入收敛到公共服务，避免聊天、本地逻辑、旧API和新编排各自修改同一事实。
- 将评估接口内部的隐式重排移交规划角色；评估产出证据和重排请求，规划生成提案，公共服务提交新版本。
- 历史接口保持兼容，但每种业务只保留一个实际写入入口。迁移期明确开关与回退方式，避免两条路径同时更新。

验收：聊天提出目标、从页面提交测评、从卡片继续任务，都能看到同一任务与最新计划；一次评估只更新一次画像和计划。

## 八、阶段3：让输入和证据真正改变计划

### T06 事件驱动的增量规划与时间约束

主责：后端；前端展示取舍。

- 先覆盖资料导入、DDL变更、空闲时间变更、评估完成、专注完成和任务状态变化事件。
- 事件持久化并携带账号、对象、时间、版本和唯一ID；小规模先用事件表与同进程处理器，启动后补处理未完成事件。
- 消费者允许重试，计划提交校验输入版本；一次输入变化产生的重复事件不得重复重排。
- 规划先校验空闲时段、课程占用、DDL与总时间，再安排优先级；必要时拆分学习任务，但不能把作业截止日期悄悄推后。
- 任务无法全部安排时返回未安排项、缺口与建议取舍。只在需要用户决策时请求补充，已有明确约束则直接执行并说明。
- 计划差异包括任务前后安排、原因、触发证据和版本。撤回以新版本恢复，保留期间已发生的完成记录；并发修改时重新校验。
- 日期按当前时间计算，覆盖今天、过期、跨天和未设置；不长期复用导入时保存的剩余天数。

验收：新增第二门课程、新DDL、60改30分钟、任务完成、低分结果分别触发合理变化；安排不超预算、不占用课程时段、不丢已完成状态；无法满足DDL时明确提示。

### T07 资料驱动练习与可查看依据

主责：后端；前端提供来源查看。

- 按账号、课程和目标知识点检索相关片段，将片段与来源ID传给出题工具，记录资料版本。
- 题干、答案解析关联文档与片段。PDF保留页码，其他格式提供段落或片段定位；无法恢复定位时如实说明。
- 校验题干与选项重复、答案结构、解析一致性，并抽样人工检查来源是否支持题目。引用ID存在不等于题目正确。
- 资料不足时返回缺口；允许用户明确选择通用知识题，界面标明来源类型。
- 外部资料作为待分析内容，不能变成越权工具指令。答案和评分标准不提前下发客户端。
- 文档向量可按内容版本和模型版本缓存，更新资料后失效重算；记录真实响应耗时与调用量。

验收：现场换一份未预置讲义仍能完成检索、出题、解析查看和评估；资料不足、不支持或解析失败时给出真实状态；第二门课程不依赖二叉树模板。

### T08 用户可理解的协作展示与异常体验

主责：前端；后端提供真实状态。

- 主界面回答“现在做什么、为什么、多久”；工程内部概念放调试或证据页。
- 复用Agent轨迹页，按目标展示角色、工作产物、证据、交接对象、状态与计划差异；不播放预设的虚假完成步骤。
- 按步骤记录模型/规则来源；在线、离线缓存、降级、等待和失败状态与实际一致。
- 资料引用可点击，计划超时有取舍，重复点击有提交状态，失败可重试且保留上下文。
- 大页面与AppState仅围绕本轮需要小步拆分；核对布局单位，验证手机、平板横竖屏与分屏。

验收：用户能从当前任务找到依据和下一动作；模型超时、断网、空数据、解析失败、权限拒绝均能继续或恢复，不出现假成功。

## 九、阶段4：鸿蒙实测、试用和交付

### T09 卡片与主动提醒

主责：前端与鸿蒙；后端维护提醒状态。

- 卡片、通知来自同一已提交任务快照，带任务ID和更新时间；完成、重排、切换账号时刷新或清理。
- 保存提醒原因、上次投递、处理、忽略和稍后提醒状态；提供静默时间、今天不提醒及开始任务，避免重复打扰。
- 按目标系统实际支持的机制安排调度，记录前台、后台、关闭应用后的实际触发范围，不宣称未经验证的持续后台能力。
- 冷启动点击卡片/通知进入对应任务；权限在使用相关功能时解释并申请，拒绝后单设备学习主线仍可完成。

验收：任务完成后不再重复提醒；重复切前后台不轰炸；数据过期有提示；拒绝权限、离线、跨天和账号切换均有记录。

### T10 双设备状态接续

主责：前端与鸿蒙；后端、测试配合。属于增强交付，设备条件成熟后纳入主演示。

- 明确账号或配对归属，核验固定会话ID的信任边界；修复首次加入后的待发送刷新与离开后的状态清理。
- 手机与平板共享稳定任务ID、状态版本和更新时间；如展示计时接续，补齐开始/暂停等计时事实与恢复确认。
- 接续后明确哪台设备负责推进，另一端如何展示；并发修改采用版本校验和明确的冲突处理，不能各自覆盖。

验收：两台真实设备完成发送、接收确认、接续、暂停、断连重连、重新进入和账号切换；日志可对应两端同一事件。若仅验证任务同步，材料就写任务同步。

### T11 模型与设备可用性、全链路回归

主责：联调测试；技术队员修复。

- 重新验证文本、向量和视觉真实调用、限额或权限错误、超时与恢复；视觉未恢复时提供文本讲义/手动错题可用路径，拍照能力保持明确状态。
- 跑正式后端全套、契约一致与行为检查、前端构建、安装启动和完整页面导航；每项分别记录通过/失败/未执行及范围。
- 真机验证网络地址、证书与权限、冷启动、锁屏计时、后台、重启持久化；设备与系统版本写入证据。
- 隔离测试账号与数据，不在真实用户资料上执行重置或实验。

验收：核心闭环与异常路径均有记录；存在的ArkTS警告按影响评估，不把能构建等同于全部功能可用。

### T12 小样本试用与收益证据

主责：产品与测试；建议在核心闭环稳定后开始。

- 可先邀请8—12位同学完成相同任务以发现可用性问题，时间允许再开展持续一周试用；人数为建议，按真实招募记录。
- 记录首次闭环成功率、操作耗时、推荐接受与执行情况、输入修正、重启保持、失败原因和人工干预。
- 记录模型成功率、响应时间分布、完整流程调用次数及费用；对比时使用相同任务与明确统计口径。
- 用户反馈与技术日志去标识化归档；材料注明人数、方法、版本和局限。

验收：有原始记录、统计表和可追溯反馈。系统掌握度加分不作为学习效果证明；如主张学习效果，需独立测验或其他独立依据。

### T13 决赛材料与可复现交付

主责：材料、集成；技术负责人复核。

- 主演示：真实讲义与DDL → 目标和诊断 → 带来源短测 → 逐点评估 → 计划变化 → 鸿蒙入口继续 → 重启保留。
- 现场变更空闲时间或新增DDL，展示系统真实适应；题数只用于演示短测，不宣称少量题即可充分证明掌握。
- 主PPT说明用户问题、Agent协作、完整过程、鸿蒙价值、验证与落地；工具权限、公式、接口及异常处理放附录。
- 依据仓库已读取规程记录，视频控制在5分钟内；正式模板、提交要求和现场答辩时长由负责人核对最新通知。
- 为在线和设备故障保留录屏及可用降级，标注录制版本，不把录像当现场实时运行。
- 更新旧打包和签名工具的历史路径，使用独立决赛输出目录、交付允许清单，排除密钥、签名密码、真实用户数据、SQLite及WAL/SHM等运行文件。
- 明确构建类型与目标设备安装要求；debug基线不直接包装成发布包。生成源码提交及未提交状态、契约版本、SDK/工具版本、HAP哈希、证书指纹、设备、测试和材料版本清单。
- 在独立解压目录验证源码启动和安装包使用，确保源码、HAP、文档、视频描述一致。

验收：按正式提交清单逐项核对；每项能力有代码入口与实测证据，未完成能力准确说明。主线不受尚未接通的视觉或双设备功能阻断。

## 十、实施顺序、并行边界与收缩策略

| 里程碑       | 纳入任务             | 退出条件                           |
| --------- | ---------------- | ------------------------------ |
| M0：共同基线   | T00              | 契约、ID、状态、样例及现有修改归属明确           |

排期由各主责人认领后给出，不在缺少人数和决赛具体日期时承诺固定工期。按里程碑逐项验收，临近冻结期只修阻断问题和材料一致性。

若时间不足：优先完成M1—M3与稳定卡片入口；推迟新增角色、复杂社交、自由多Agent讨论和完整双设备计时接续。可信华为登录与视觉模型完成前保持准确状态，保留其他已验证路径。

## 十二、队员接到任务后立即执行

1. 阅读本任务书及首轮基线记录，确认工作目录与本机环境。
2. 认领任务ID，写明主责人、协作人、依赖、预计完成时间和阻塞。
3. 先对齐契约与样例，再改动跨前后端的数据结构；已有功能保持可回退。
4. 每完成一个任务提交可重复验收步骤与证据，更新状态；不凭截图或口头“已完成”关闭任务。
5. 每轮联调统一更新已实现/已验证/待完成清单，材料负责人据此同步文档和PPT。
