# 知学 Mate：Agent 特点与协同改造方案

日期：2026-10-21。本文为修改建议，未实施业务代码改造。依据当前工作区的 Agent、聊天、工作流与工具实现，以及《决赛评估与改进建议》《开发基线与首轮修复》；旧评估中的问题需按首轮修复记录更新状态。

## 1. 改造目标

将产品主线聚焦为：**学习秘书接收目标与约束，协调诊断、规划、练习和评估，根据真实学习证据持续调整下一步任务，并将同一任务同步到鸿蒙入口。**

老师指出的两个问题需要分别解决：

- Agent 特点：能够围绕目标观察状态、选择工具、执行动作、根据结果调整；有记忆、边界和停止条件。
- 协同性：不同角色交换有依据的工作产物，能够请求补充、反馈冲突、修改方案，共同完成一个用户目标。

保留现有五个角色和技术栈。第一阶段不增加新角色、不迁移框架、不让所有角色互相自由对话。模型负责语义理解、诊断假设和策略提案；工具负责检索、校验、评分、排程和持久化。受控工作流仍是可靠执行的基础。

## 2. 当前实现为什么显得像功能拼接

| 当前证据 | 具体问题 | 修改方向 |
|---|---|---|
| `app/runtime/orchestrator.py` 按 profile、plan、pendingSubmission 等字段选择下一步 | 主流程以“是否已有数据”为依据，难以表达证据不足、目标冲突、执行失败后的不同策略 | 增加目标、约束、证据充分性和任务结果驱动的决策 |
| `app/agents/secretary.py` 主要包装下一步选择；工作流循环直接调用决策器 | 秘书角色与实际协调职责脱节 | 秘书成为编排服务的策略入口，统一委派、等待、汇总和停止 |
| `DiagnosisAgent` 统计 evidence 的错误次数与类型，但编排主要在缺少画像时进入 diagnosis | 已有账号获得新证据后，未形成清楚的再次诊断路径 | 根据错题、评估和新资料事件重新诊断，区分事实与假设 |
| `PlannerAgent` 初始任务统一30分钟 | 缺少可用时间、DDL、课程占用等硬约束，计划个性化不足 | 候选方案经过确定性排程校验后才提交 |
| `_persist_workflow_assessment` 直接调用重规划规则，随后返回 `needReplan=False` | 评估影响计划，但真实执行绕过规划角色，轨迹难以说明协作 | 评估提交结果与重排请求，由规划角色消费，统一提交计划变更 |
| `/api/agent/chat` 调用 `chat_llm.chat`；`/api/v1/workflows` 运行另一条执行链 | 聊天能理解请求，却缺少统一的目标执行上下文 | API 保留兼容入口，内部接入同一个学习应用服务 |
| 资料检索、出题、专注和提醒已有各自入口 | 上游结果未持续约束下游行为，部分状态仅在本地 | 统一事件、任务ID、证据引用与版本 |

上述问题不意味着现有工作流没有价值。状态版本、等待答案、工具权限、确定性判分和 trace 都应复用。

另外，`_agent_action` 的“缺少画像”分支仍含二叉树42分的演示初始化，应与正常注册账号的空画像路径一起清理，改为收集课程或发起基线测评。

## 3. 五个角色的实际职责

| 角色 | 独立负责的问题 | 接收 | 交付和交接 |
|---|---|---|---|
| 学习秘书 | 当前目标下一步需要谁做什么，何时询问用户或结束 | 目标、约束、事件、各角色结果 | 子任务、依赖、成功标准、下一动作；信息不足时发起补充请求 |
| 学情诊断 | 已有哪些证据，哪些结论还不能成立 | 资料知识点、错题、逐知识点评估、历史证据 | 诊断报告、证据ID、置信说明、待验证假设及建议测评 |
| 学习规划 | 在有限时间内如何优先达成目标 | 诊断报告、DDL、空闲时段、任务进度 | 可执行计划提案、约束校验结果、取舍及版本差异 |
| 练习辅导 | 用哪些材料和练习验证或改善目标知识点 | 目标知识点、错误类型、预算、资料引用 | 有来源的题组或补救练习；资料不足时返回缺口 |
| 学习评估 | 本次结果能够支持怎样的画像更新和后续建议 | 答案、题目、逐知识点旧画像、证据 | 确定性评分与逐点更新、证据充分性、继续/补测/重排建议 |

“独立”指职责和产物明确，不要求每个角色独立进程或每步调用模型。规划可以调用一次模型提出取舍，再用确定性工具校验；评估的评分核心继续使用代码。资料检索先作为诊断、练习可调用的工具，提醒和搭子匹配先作为可按需调用的能力。

## 4. 将固定串行改为有交接与反馈的协作

推荐采用“秘书协调＋共享上下文＋结构化交接”，单体后端内即可实现。

### 4.1 最小协作协议

子任务包含：`taskId`、`goalId`、`owner`、`objective`、`dependsOn`、`inputRefs`、`constraints`、`expectedOutput`、`inputVersion`。

角色结果统一包含：

- `status`：完成、需补充信息、证据不足、约束冲突、工具失败。
- `artifactRefs`、`evidenceIds`：产物与依据，使用结构化引用。
- `summary`、`reason`：可展示的结论及简短依据。
- `nextRequest`：请求哪个角色继续做什么，交由秘书校验和调度。
- `toolCalls`、`decisionSource`：实际工具记录与模型/规则来源。

`nextRequest` 不是任意执行权限。运行时检查角色权限、依赖、输入版本和预算，通过后才执行。标准答案留在服务端评估工具可读的存储中，不进入公共上下文或客户端轨迹。

### 4.2 三条必须跑通的反馈路径

1. **诊断→练习→评估→诊断**：证据不足，先安排短测；评估后复核原假设，决定补救或进入学习任务。不能把未测评的0分直接作为薄弱结论。
2. **规划→秘书→用户约束→规划**：计划超出空闲时长时，明确列出无法安排的任务和取舍；必要时询问用户。新增DDL或空闲时间改变也触发这条路径。
3. **评估→规划→秘书**：结果满足重排条件后，由规划角色生成调整提案，秘书汇总，再按产品策略提交并展示差异。禁止在评估接口内隐式完成全部重排。

并非每次必须经过五个角色。查看今日任务可以直接读计划；仅修改空闲时间可直接重规划；反复答错且原因不明时才重新诊断。独立的资料检索与日程读取可以随后并行；影响画像或计划的写入按依赖和版本顺序提交。

### 4.3 循环和成本边界

沿用现有步数上限，并增加每个目标的模型调用、工具重试和总耗时预算。相同证据下反复请求相同动作时停止循环，返回已完成部分及待补信息。超时可恢复，不能只展示“正在协同”。预算数值通过真实调用延迟测量后确定。

## 5. 让共享记忆有事实基础

按用途划分三类状态，保持当前仓储兼容，逐步迁移：

1. 用户事实：课程、DDL、空闲时间、资料归属、任务进度。用户自评保存为声明，不直接覆盖测评掌握度。
2. 学习证据：答题结果、错题、资料片段、逐点分数及置信信息。专注时长记录执行投入，不能直接证明掌握。
3. 执行状态：目标、子任务、等待原因、角色产物、版本、幂等键和失败恢复点。

事件先覆盖：`MaterialImported`、`DeadlineChanged`、`AvailabilityChanged`、`AssessmentCompleted`、`FocusCompleted`、`TaskStatusChanged`。事件记录账号、事件ID、对象ID、发生时间和版本。

落地时先用数据库事件表、待处理任务表和同进程处理器，无需先引入消息中间件。状态变更与事件写入保持事务一致；消费者允许重试，通过幂等键避免重复更新。旧版本的模型结果不得覆盖用户最新修改，应重新校验或重算。

聊天、练习、专注、导入和鸿蒙入口共同调用学习应用服务。API 层处理身份、请求校验和响应，业务服务负责事件和提交。逐步把前端独有课程、DDL、完成状态同步到服务端；离线采用待同步队列并明确冲突策略。

## 6. 与此前问题合并处理

| 事项 | 当前口径 | 在本方案中的位置 |
|---|---|---|
| 账号访问控制 | 首轮已修复部分后端边界；可信华为登录暂禁用，账号切换缓存与异步结果仍待验收 | 新增事件、记忆、子任务、引用和订阅沿用同样的归属规则 |
| 多知识点评估共用旧分 | 仍待修复；工作流中也有取画像第一条旧分的路径 | 改为逐知识点旧分、题量、结果与证据，两条提交路径共用服务 |
| 专注和任务状态持久化 | 仍待完成闭环 | 先持久化唯一执行事件，幂等补交；重启和离线恢复可验收 |
| 导入或修改后计划不持续变化 | 仍待处理 | 数据提交产生事件，规划角色消费；保留已完成任务 |
| 重排可突破总时间 | 仍待处理 | 排程工具校验空闲时段、DDL和总时长，冲突显式返回 |
| 资料未贯通出题与解释 | 仍待处理 | 检索片段进入练习上下文，保存引用；引用存在不代表内容正确，仍需校验与抽样复核 |
| 长期关闭后的提醒 | 尚未验证完整调度 | 先做提醒状态、去重、静默与稍后处理；实际触发范围按设备验证说明 |
| 跨设备 | 已有任务同步代码，完整状态接续待实测 | 同一任务ID、版本和计时事实接续，处理账号及并发冲突 |
| 在线视觉模型 | 基线记录仍未解决 | 核心演示先支持文本讲义和手动输入错题；恢复并验证后再纳入拍照主线 |

原评估“暂缓增加新角色”的建议继续适用。本次增强已有角色的责任和协作协议。

## 7. 前端如何让用户看到协同价值

主界面优先展示“现在做什么、为什么、预计多久”。为当前目标增加可展开的协作记录，复用 `AgentTrace.ets`：

- 已收到：今晚30分钟，明天作业截止。
- 诊断结果：遍历题证据不足，需要短测。
- 规划结果：先完成作业，保留短测，暂缓拓展练习。
- 练习结果：题目引用某份讲义的具体片段。
- 评估反馈：哪一知识点有哪些证据变化，是否需要再次诊断。
- 计划差异：哪些任务改变、原因、当前版本。

每项显示真实状态：执行中、等待回答、缺少资料、失败可重试、已完成；只有真实调用完成才标记完成。模型与规则来源按步骤记录，不能用一次 `llmUsed=true` 代表整条链由模型决策。

轨迹展示结构化决策摘要、工具结果与证据，避免输出模型隐藏推理。卡片和通知来自已提交的任务快照，带任务ID和更新时间；点击回到同一任务并恢复上下文。

## 8. 实施批次与代码落点

| 批次 | 后端 | 前端 | 完成标准 |
|---|---|---|---|
| 1：修事实与状态 | 逐点评估；统一评估提交服务；任务与专注事件持久化；清除正常路径的演示分数 | 区分未测评/已诊断；完成记录同步与重启恢复 | 多知识点不会互相覆盖；重复提交只计一次；重启状态保留 |
| 2：打通协作主线 | 扩展 `AgentResult`；秘书与运行时协作协议；将隐式重排移交规划；聊天接入同一应用服务 | 目标ID贯通聊天、计划、练习和轨迹；真实等待和失败状态 | 评估结果产生可追踪的规划请求；不同条件产生不同路径 |
| 3：增强决策质量 | 资料检索接入练习；时间约束排程；资料、DDL和空闲事件触发规划 | 来源查看、计划取舍、版本差异；必要的约束补充 | 新讲义可出有依据的题；60变30分钟后计划不超时 |
| 4：鸿蒙与决赛证据 | 提醒持久状态、任务版本和接续支持；指标采集 | 卡片进入同任务、稍后提醒、真实设备接续 | 权限/离线/重启/账号切换有记录；材料与实测一致 |

主要落点：`app/agents/` 明确角色输入输出；`runtime/orchestrator.py` 和 `loop.py` 支持交接与反馈；`runtime/tool_registry.py` 增补检索与排程工具、参数校验和权限；`api/chat.py`、`workflows.py`、`exercises.py` 改为调用公共服务；`domain/`、`repositories/` 增加目标、子任务和事件状态。

契约真源与前端镜像同步更新。新增字段先保持旧响应兼容，逐步切换读写；避免旧接口和新编排同时提交画像或计划，迁移期明确每种操作的唯一写入入口。当前含未提交的访问控制和签名配置改动，实施时应保留并单独审阅。

## 9. 核心演示与验收

主场景：用户提出“明天交数据结构作业，今晚只有60分钟”，上传一份新讲义。秘书建立目标，诊断识别证据缺口，练习生成有来源的短测，评估逐点更新，规划据此分配任务。用户临时把时间改为30分钟，规划明确保留和推迟内容。完成任务后重启，卡片与应用仍指向同一任务和状态。

为验证动态协同，至少增加以下对照：

| 条件变化 | 应有行为 |
|---|---|
| 没有测评证据 / 已有充足证据 | 前者补测，后者可以直接规划，轨迹说明不同路径 |
| 同样目标，答对 / 连续答错 | 产生不同的后续学习动作；样本不足时保留不确定性 |
| 可用时间60→30分钟 | 已提交计划不超过预算；无法完成部分显式列出 |
| 资料不足或引用不支持题目 | 返回缺口或重新生成，不能伪造来源；通用题需明确标识 |
| 推进重试、重启恢复、同事件重复送达 | 不重复记账，沿当前状态继续 |
| 用户改约束时旧模型结果返回 | 拒绝旧版本覆盖，按最新约束校验 |
| 模型超时、离线、权限拒绝 | 展示真实降级、等待或失败，可继续或恢复 |
| 甲/乙账号切换 | 轨迹、引用、任务、卡片和异步结果归属正确 |

记录任务完成率、约束满足率、引用支持情况、计划响应延迟、重试重复计数和人工纠正次数；模型调用次数与耗时同时记录。先建立当前版本基线，再以同一组场景比较改造版，不预写改善百分比。

答辩核心表述建议：**“五个角色围绕同一个学习目标交换证据和任务结果；信息不足时补测、时间冲突时调整、执行后重新评估。模型提出策略，工具保证计算与状态可核验，鸿蒙入口承接同一个任务。”** 所有能力按实际验收状态表述。
