## 3. 关键设计说明

### 3.1 Embedding 分批不改变检索契约

`rerank()` 仍一次提交 `[query, *texts]` 给编码器，编码器内部透明拆成不超过 10 条的 HTTP 请求。每批的 `index` 从 0 重新编号，因此必须在每批内部排序后再依次拼接。最终向量数量只要与有效文本数不一致，就返回 `None`，上层继续以 `keyword+tag` 模式诚实降级。

### 3.2 视觉模型不再继承文本模型

文本模型可能被切换为 DeepSeek 等不支持当前 `image_url` 链路的模型。`LLM_VL_MODEL` 缺失时若复用 `LLM_MODEL`，拍照识题会在配置看似正常时失败。因此视觉默认值固定为已在本项目配置中使用的 `qwen3-vl-plus`，并保留显式环境变量覆盖能力。

### 3.3 依赖约束与运行环境

本机实际环境：Python 3.12.13、PyMuPDF 1.24.11，未安装 onnxruntime。约束 `<2` 能保证重新安装依赖时不会进入第七批报告中 Python 3.14 + PyMuPDF 2.0 的原生崩溃组合；它不替代锁文件，后续仍建议形成可复现依赖清单。

## 5. 未实施与剩余风险

1. 多进程提交幂等仍依赖进程内 `RLock`，没有数据库唯一约束与跨进程事务；本批未冒险修改仓储语义。
2. 交卷解析超过预算后的 LLM 结果仍会丢弃，且每次提交启动独立 daemon 线程，没有并发上限。
3. 出题仍为同步调用且无短期缓存；关闭思考后虽明显改善，但网络波动时仍可能达到超时。
4. SDK 自动重试默认关闭后，429/5xx 没有总预算内的有界重试。
5. 决策适配器固定 8 秒超时，模型调用仍缺少统一耗时、token 与降级原因日志。
6. 本批没有构建 HAP、没有进行真机/模拟器 UI 和双设备验收，也没有进行真实 DashScope 200 切片在线验证。
