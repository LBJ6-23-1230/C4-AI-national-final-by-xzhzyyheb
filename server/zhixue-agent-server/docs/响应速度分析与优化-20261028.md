# 响应速度分析与优化（2026-10-28）

## 范围与证据

检查主开发目录的聊天、学情画像、学习工作流、模型调用和前端等待反馈。未修改同级 `github-upload-20261027` 快照。本次没有调用线上模型或修改部署，结论区分代码链路分析与实际性能测量。

## 为什么慢

1. 普通文字聊天原先先调用模型分类，再调用子 Agent 生成答复，串行消耗两次远程请求时间。每次调用分别有默认 30 秒预算，并非整个聊天共享 30 秒。两次调用都较慢时，总等待可能接近 60 秒，前端默认聊天读超时下限为 40 秒，存在前端先超时的风险。
2. `/api/agent/chat` 使用完整 JSON 响应，`AgentBridge` 等完整响应后才展示回复，没有流式首字反馈。此前 `ChatBubble` 只显示三个静态圆点，无法区分正常等待与卡住。
3. 请求明确要求开始学习、生成计划时，聊天回复后还会同步执行 `ensure_chat_context`，完成工作流推进后才返回。普通“查看薄弱知识点”不满足这个触发条件，不应将所有学情查询都归因于工作流。
4. `StudyTags` 的画像读取本身是 `getProfile`，有前端缓存；“开始诊断”另需创建工作流、推进工作流。非聊天协调工作流还可逐步调用模型决策，因此需要区分“读取画像”“解释画像”“启动诊断”的耗时。
5. 共享模型执行池为 8 个线程、最多 24 个在途或排队任务，并发增加时可能排队。超时能停止调用方等待，但不能强制终止已经开始的同步网络请求。这是代码层面的潜在压力点，尚未用线上并发数据确认其占比。
6. 通用上下文包含历史、用户资料、课程、任务、错题证据。数据量增加可能增加模型处理耗时；本次保留全部既有上下文，以免丢失诊断证据。

本地配置已经设置 `LLM_ENABLE_THINKING=0`，文本/决策模型为 `qwen3.8-flash`，并已有连接池复用、超时预算和部分解析后台回填。不能把这些已有机制当成本次新增，也不能把界面的“思考中”直接解释为模型正在输出思维链。

## 已实施

- 对五条固定快捷入口文案做严格完整匹配，直接进入既有子 Agent。包括学情画像、今日建议、学习搭子、今日任务、更新画像。末尾常用句末标点可忽略；否定、附加要求和自由输入仍由原分类器判断。
- 有当前用户、当前会话待确认事务时，确认/取消先走既有确定性事务逻辑，跳过此前无意义的分类请求。没有待确认事务时不改变原语义。
- 快捷入口仍调用原模型生成分析，保留真实画像、历史、证据、结构化结果、确认流程与失败降级。没有缩短回答 token 上限，没有更换模型或降低评分要求。
- 聊天气泡增加动画与已等待秒数，离开时清理计时器。只展示真实等待时间，不伪造“已完成分析”等服务端阶段，也不把它称作流式输出。
- 模型日志区分 `intent`、`weakness`，记录 `queue_ms`；聊天日志增加 `chat_pipeline` 的回复处理、协调工作流与总耗时。不记录提示词、用户标识、密钥和回答内容。

## 验证与收益边界

聊天、快捷入口、学习上下文、时间预算和工作流恢复共 119 项测试通过（9.11 秒）。新回归覆盖快捷入口一次调用且保留画像证据、自由输入继续分类、模型失败如实降级、取消操作跳过分类并保持会话范围。

前端 ArkTS 编译与 debug HAP 打包通过（BUILD SUCCESSFUL）。构建提示未配置签名，产物未安装到真机，也未发布。等待动画的真机视觉效果尚未验收。

可确定的收益：固定学情入口的模型请求次数从 2 次减少到 1 次；其节省时间等于原意图分类请求的耗时。确认/取消操作减少 1 次分类请求。模型请求次数减半不代表用户总等待减半。测试运行时间也不是实际模型响应时间。

## 后续性能验证与进一步优化

部署后按 `request_type` 对比相同模型、相近输入长度和并发条件下的 P50/P95。先看 `intent` 与 `weakness` 耗时，再看 `queue_ms` 和 `coordination_elapsed_ms`，避免将网络、排队、生成、工作流等待混为一谈。

自由输入还保留两阶段请求。进一步改善首字体验需要端到端流式协议或异步任务接口，同时处理卡片 JSON、身份切换、取消、错误、历史落盘和画像事务完成时机。该改造应单独进行契约与真机验证。工作流锁的缩小也需要先验证并发写入一致性。本次保留这些行为，避免以提速为由破坏功能。
