# 同步冲突：要不要做？

> 评估对象：`参考图/05-课程与作业.jpg` 的 05D「检测到同步冲突」弹窗（V2 视觉提案）。
> 评估日期：2026-11-03。
> 结论先说：**要做，但只做“最小诚实版”；不要按 05D 原样实现，赛前也不要碰字段级合并。**

---

## 0. 三句话

1. **这不是新功能。** 409 版本冲突、离线队列、两个解决动作、本机备份写入（只有写入，没有恢复入口），代码里都已经有了；缺的只是“让用户看得见、选得明白”的界面。
2. **现状是一个必现死角。** 冲突一旦发生，课程/作业同步会整体停住；提示只出现在课程页顶部的一行 12vp 小字，用户在别的页面完全无感。
3. **设计稿方向对，但位置、文案、备份承诺三处会误导：** 弹窗挂在 05D（不是真实触发点）、把“记录级合并”说成“覆盖云端”、“备份为历史版本”实际没有恢复入口。按最小版做约 1–1.5 人日（弹层 0.5–1 + 诚实性修复 0.5）；完整合并器 3 人日以上，赛前不值得。

## 1. 现状核查：功能已经在，缺的是 UI

| 能力 | 现状 | 位置 |
|---|---|---|
| 逐记录版本冲突检测 | 服务端按 `expectedVersion` 校验，任一记录过期即整批 409 | `server/zhixue-agent-server/app/services/learning_data.py:171` |
| 冲突错误码 | 409 `CONFLICT`，「其他设备有更新，请确认后同步」 | `server/zhixue-agent-server/app/api/learning_data.py:19` |
| 离线队列 / 幂等键 / 重放 | 已实现，队列随账号快照持久化 | `app/entry/src/main/ets/services/LearningSync.ets:107` |
| 冲突态全局标志 | `engine.conflict` → `AppStorage('learningSyncConflict')` | `app/entry/src/main/ets/data/AppState.ets:85` |
| 两个解决动作 | `keepLocalLearningChanges()` / `useServerLearningData()` | `AppState.ets:91-122` |
| 现有的冲突 UI | 课程页顶部一行小字 + 两个文字链接（12vp） | `app/entry/src/main/ets/pages/CourseImport.ets:735-748` |
| 双设备冲突测试 | 已有 HTTP 级用例：A 改名后 B 提交旧版本 → 409 | `server/zhixue-agent-server/tests/test_learning_sync_feedback.py:140` |

**这意味着：** 工作量不在同步协议，而在一个弹层、文案、冲突条目展示，以及把已有动作接上去。把它当成“从零做一个同步冲突功能”会高估成本；把它当成“换个皮肤”又会低估文案与可恢复性的风险。

---

## 2. 什么时候会真的发生

触发需要同时满足四个条件：

1. 同一账号登录两台及以上设备；
2. 其中一台有**未上传的队列**（离线编辑、同步失败、写本地后进程被杀）；
3. 另一台在这段时间里改了**同一条**课程或作业；
4. 第一台恢复网络后重放队列。

以下情况**不会**冲突，容易误判：

- 单设备：不会。
- 两台设备改的是不同记录：不会。服务端按记录比较版本，互不影响。
- 首次登录/换机迁移：`migration: true` 只增不覆盖，不会 409。
- 同一个请求重试：幂等键返回上次结果，不会 409。

所以这是**低频**事件。没有埋点，给不出真实比例；按触发条件推断，绝大多数单设备用户永远遇不到。但它一旦发生，不是“提示一下”那么简单（见下一节）。

### 2.1 设计稿把弹窗放在 05D，是“就近取景”

05D 是「识别校正与确认」，属于**新导入**。OCR 的课程 ID 由服务端按时间戳生成（`server/zhixue-agent-server/app/api/schedule_import.py:48`，形如 `ocr-<时间戳>-<序号>`），文件导入同理（`FileParserService.ets:174`、`:216`）。两台设备各导一次同一张课表，会生成两条不同 ID 的课程（表现为重复课程），**不会触发 409**。

真正会冲突的是：

- 05A 编辑一门**已同步**的课程（改名、改考试日期、改优先级）；
- 05B 完成或删除一条**已同步**的作业；
- 删除一条已在云端存在的记录。

因此冲突弹窗如果只挂在 05D，真实场景里大概率根本弹不出来。它应该挂在**全局同步状态**上，05D 只是“碰巧被画在这里”。

## 3. 不处理的代价

- `LearningSync.run()` 在 `conflict` 为真时直接返回，**队列不再上传**；`syncLearningData()` 也不会再拉云端最新数据。
- 提示只写进 `learningSyncMessage`，而全项目只有 `CourseImport` 读了它；用户在对话页、计划页、专注页都看不到。
- 重启后 `conflict` 不持久化，登录时会自动重试；仍然 409，于是又静默进入冲突态。用户看到的现象是“同步一直不成功”，但不知道为什么。
- 用户继续编辑，`capture()` 继续往队列里加；等真正解决时，要处理的记录比最初更多。
- 若用户选了“使用云端并备份本机”，本机快照被写到 `conflict-backup-<userId>-<时间戳>` 这个 preferences key；`LearningDataStore.load()` 只按真实 userId 读，**没有任何入口能列出或恢复它**。文案承诺的“备份为历史版本”在用户侧不成立。

低频，但高损，而且是“数据可能被覆盖”的信任问题。**这已经不是一个可选的体验优化，而是现有跨设备同步的一个兜底缺口。**

---

## 4. 设计稿逐条问题

| # | 问题 | 严重度 | 说明 |
|---|---|---|---|
| D1 | 两个选项没有任何差异信息 | 高 | 不告诉用户“哪几门课冲突、云端是什么、本机是什么、哪台设备/什么时间”，只能盲选。对不可逆操作，这是硬伤。 |
| D2 | “保留本机修改（推荐）”的“推荐”没有依据 | 高 | 实际动作是：本机队列里的记录**整条覆盖**云端同 ID 记录，云端那一版内容不保留、无历史。若另一台设备改的是同一门课的另一个字段（如考试日期），也会被一起覆盖。没有时间戳，无法判断哪边更新。 |
| D3 | 文案把“记录级合并”说成“整表覆盖” | 中 | `keepLocal()` 会把队列记录重定位到云端最新版本再提交，**只覆盖本机改过的记录，其他云端记录保留**。这其实是一个还不错的“本机优先合并”，但标题「云端与本地存在不同的课程数据」+ 副标题「覆盖云端」写得像整表覆盖，既吓人又不准确。 |
| D4 | “备份为历史版本”不可兑现 | 高 | 只 `save` 不 `load`，没有列表、没有恢复入口，也没有版本概念。答辩时被追问“历史版本在哪看”会很难答。 |
| D5 | 位置错：只挂在 05D | 高 | 冲突的真实触发点是 05A/05B 的编辑；挂在 05D 会漏。且弹窗会打断“确认导入”这个当前任务。 |
| D6 | “取消”语义不清、按钮不具名 | 中 | 取消后同步仍是停的，但没有持续提示；“确定”没有说明会做什么。破坏性操作的主按钮应写“合并并同步 / 改用云端”，而不是“确定”。 |
| D7 | 现有实现的危险不对称 | 中 | 当前代码里“保留本机修改”会先弹 `AlertDialog` 确认，而更危险的“使用云端并备份本机”**点一下直接执行**（`CourseImport.ets:739`）。新设计至少应把两者拉平：都要具名、都要说明后果。 |

补充：提案里 05A 已经有「上次同步：今天 08:05 · 重新同步」这一行。**那才是冲突状态最自然的宿主**：平时显示同步时间，冲突时变成“1 项冲突待处理”，点开进解决页。05D 不需要承担这个全局状态。

## 5. 多角度打分

| 角度 | 判断 | 说明 |
|---|---|---|
| 用户价值 | 中 | 低频，但发生时直接决定“数据丢不丢”。属于水电煤式的必备能力，不是卖点。 |
| 发生频率 | 低 | 需同账号双设备 + 同记录 + 一方离线/失败。单设备用户永远遇不到。 |
| 失败代价 | 高 | 同步停摆、跨页无感、可能整条覆盖云端、备份不可找回。 |
| 实现成本 | 低 | 动作、状态、409、测试都已存在；主要成本是弹层 + 文案 + 冲突条目名。 |
| 演示价值 | 低–中 | 现场触发需要两台设备 + 离线 + 重叠编辑，视频里不值得演；作为文档/答辩里的“状态完备”证据更合适。 |
| 维护成本 | 低 | 做成一个全局组件即可；做成 05D 专用弹窗才会产生重复逻辑。 |
| 与 V2 设计系统的一致性 | 高 | 正好补上 `StateView` 的“冲突”态，也是提案里少数**有真接口支撑**的状态，不是写死文案。 |

**综合：性价比高，但不该重投入。** 它是“把已有能力补成可见、可决策、可恢复”的收尾工作，不是新功能战役。

> 顺带修正一处文档判断：`design-contract.md` 的 R5 写“等待、冲突无接口支撑，只能写死文案”。对课程/作业同步冲突来说这是**不成立**的——409、版本号、幂等、双设备测试都是真的。建议把这一条改成“冲突有接口，缺 UI”，否则容易被误判为“展示数据”而砍掉或造假。

## 6. 建议方案

### 6.1 最小可用版（推荐，约 0.5–1 人日）

**形态**：全局一个 `SheetShell`（或 `CustomDialog`），不放在 05D 页面里；由 `AppState` 的冲突态驱动，任何页面都能弹。

**触发**：`learningSyncConflict === true`。同时 05A 的同步行常驻显示「1 项冲突待处理」（即使本次点了“稍后”）。

**内容**：

```
检测到同步冲突
本机有 3 条课程/作业修改未上传，其中 1 条与云端版本冲突。

冲突记录
· 数据结构（课程）  你改了：考试日期 11月10日 → 11月12日
· 操作系统（课程）  …

[ 合并并同步 ]  本机改过的记录优先，其余用云端
[ 改用云端 ]    放弃本机这 1 条修改（先备份）
[ 稍后处理 ]    同步将暂停，可从课程页的同步状态再次进入
```

**规则**：

1. 不预选、不写“推荐”。没有时间戳就无法判断哪边更新，盲推等于替用户做不可逆决定。
2. 按钮具名：`合并并同步` / `改用云端` / `稍后处理`，不用“确定”。
3. “改用云端”前二次确认，并明确“本机这 1 条修改将不再上传”。
4. 冲突条目名：客户端拉一次 `GET /learning-data`，把队列里每条记录的 `syncVersion` 与云端当前版本比较即可得到，**不必改服务端**。最多列 3 条，其余折叠为“等 N 条”。
5. 关闭弹层 ≠ 解决冲突：保留 `learningSyncConflict`，在 05A 同步行持续显示待处理。

### 6.2 诚实性修复（必须，约 0.5 人日）

二选一，不能两个都不做：

- **A. 把备份做成可恢复**：`keepLocal` 前也保存一份云端快照；设置/课程页加“同步备份”入口，可查看时间、条数并恢复。这样“备份”才成立，也才敢把“合并”作为默认。
- **B. 删掉“历史版本”承诺**：文案改成“改用云端后，本机这 N 条修改将不再上传”，并在确认框里写明。至少不骗人。

推荐 A；如果赛前只剩几天，至少做 B。

### 6.3 不要做（赛前）

- 字段级 diff / 三方合并 / 逐字段选择：约 3 人日以上，收益远低于同样时间投入 P0 的登录、对话、学习页。
- 冲突历史列表、自动合并策略、按设备维度的版本树。
- 为 05D 单独做一个弹窗（会和全局状态重复）。

### 6.4 排期建议

| 剩余时间 | 做法 |
|---|---|
| 2 周档 | 跟 `StateView` 一起做，放在 P1 末尾（约 1–1.5 人日）；05D 的表格→卡行仍是 P2，不占这个工时。 |
| ≤1 周 | 只做两件事：① 把现有 `CourseImport` 那两个小字链接改成一个明确入口；② 05A 同步行加“冲突待处理”状态。弹窗留到赛后，截图/文档里可用提案图并标注“设计稿”。 |
| 3 周+ | 6.1 + 6.2 A，再考虑把 `updatedAt` 加进快照，显示“本机 14:02 / 云端 14:05”。 |

## 7. 什么情况下可以不做

只有这三种前提之一成立，才可以砍：

1. 产品明确“跨设备只做只读/备份”，客户端不写课程/作业；
2. 同步改成“服务端权威、客户端不产生离线队列”；
3. 明确只支持单设备，跨设备同步不作为能力宣传。

否则不建议砍：它是现有同步链路的兜底，不是锦上添花。

---

## 8. 需要拍板的 4 件事

1. **默认动作**：合并（本机优先）还是改用云端？建议**不预选**，让用户明确选。
2. **备份承诺**：补恢复入口（A），还是删掉“历史版本”（B）？
3. **冲突明细**：客户端比较版本（0 后端改动，推荐），还是服务端 409 返回 `details`（更权威，但要同步两份契约 + 测试）？
4. **宿主位置**：全局 Sheet + 05A 同步行（推荐），还是按提案放 05D？
