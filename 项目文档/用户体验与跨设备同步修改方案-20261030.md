# 知学 Mate 用户体验与跨设备同步修改方案

日期：2026-10-30
依据：用户提供的五张截图、用户确认各设备使用自己电脑上的后端，以及当前 `main` 分支 `d888543` 的代码。
交付范围：修改方案与验收标准。本次检查包含静态代码核对、只读数据库检查和纯内存复现；未实施业务代码修复或修改数据库。

## 一、结论与修改顺序

建议先修复“操作结果误判”和“跨设备空数据覆盖”，再调整页面与测评口径。仅隐藏报错、折叠卡片，无法解决按钮看似失败和课程/DDL 缺失的问题。

| 优先级 | 问题 | 本次核实结果 | 目标 |
| --- | --- | --- | --- |
| P0 | 提醒按钮显示契约不一致 | 前端将允许为空的字段按非空字符串校验；合法响应可能被判失败 | 正确识别操作结果，页面只呈现简短反馈 |
| P0 | 同账号换设备看不到课程/DDL | 原始课程、DDL 主要保存在设备本地；登录只恢复本地账号快照 | 服务端保存完整业务数据，任一设备登录后恢复 |
| P0 | 新设备可能移除原有计划作业 | 读取计划前先上传本地 DDL 快照；空快照会移除计划中的 DDL 任务，已用内存数据复现 | 读取无写入副作用；空缓存不能表示删除 |
| P1 | 今日重点占据过多首屏 | 现有展开开关只控制推荐理由与后续任务，没有折叠整张卡片 | 首次展示引导，之后默认收起并保留注意提示 |
| P1 | 知识点名称、粒度与状态混乱 | 名称完全相同才容易去重；未测评初始化为 0；按分数混排 | 按课程和主题组织，统一“未测评/初步结果/需巩固”等状态 |
| P1 | 测评入口与实际内容不一致 | 测评入口跳到行为复盘页；0 分钟与 40% 分别来自今日和历史口径 | 区分学习投入、练习表现和后续验证 |
| P2 | 学习效果结论证据不足 | 现有掌握度采用固定增减分，不能直接代表能力或学习增益 | 以真实答题、前后对比、延迟复测支持结论 |

截图中实际发生过哪些服务端写入，仍需结合对应账号的请求和历史记录确认。内存复现证明存在覆盖路径，不等于本次检查已经证实截图账号的数据被该路径移除。

## 二、图一：今日重点收起、展开与操作反馈

### 2.1 页面行为

首次在该设备完成账号登录后，展示一次展开卡片；后续进入对话页、刷新、切换底部导航时默认收起。用户主动展开或收起时保留本次选择，普通接口刷新不能重置展开状态。账号切换后读取对应账号的界面偏好。

收起时只占一条紧凑提示栏，例如：

```text
! 今日有 1 项待处理                         展开 ∨
```

有临近截止事项时，提示可以替换为“有作业即将截止”。颜色、图标与简短文字共同表达注意状态，不靠持续的大面积红字制造紧迫感。没有待处理事项时显示“今日暂无待处理事项”或不占首屏位置。

展开后保留：任务标题、所属课程、截止时间或预计时长，以及“开始任务 / 稍后30分钟 / 今天忽略”。“为什么建议现在做”放在二级展开内容内。提醒设置入口保留在展开卡片或更多菜单中。

首次引导标记、展开偏好属于设备界面状态；任务、稍后提醒、忽略等属于账号业务状态，应跨设备同步。紧急事项在收起状态持续显示注意标记，但不因轮询反复自动展开。

### 2.2 先修复合法响应被拒绝

`ApiResponseValidator.isReminder()` 对所有字符串调用 `hasString()`，而该函数要求去除空白后长度大于 0。契约中的 `courseName`、`planId`、`knowledgePointId` 仅要求为字符串，并未要求非空。后端确实存在这些字段为空的合法场景，例如普通学习间隔提醒。

本次只读查看到 12 条提醒事件，其中 3 条 `courseName` 为空，1 条 `planId` 为空，1 条 `knowledgePointId` 为空；这些情况都会触发现有前端校验失败。该统计不包含个人内容。

修改要求：

1. 按字段语义校验：事件 ID、账号 ID 等必须非空；不适用的关联字段允许空字符串；枚举、数值、必要字段继续严格校验。
2. 同时覆盖今日概览、提醒列表和操作响应，统一 OpenAPI、前端模型、模拟数据与校验器。
3. 保留契约校验，不能用“所有响应直接放行”掩盖结构问题。
4. 处理“服务端成功、客户端响应校验失败或超时”的不确定状态：先读取事件状态确认；只有确认未成功时才提示失败。需要重试时沿用同一幂等键，避免重复执行。

### 2.3 用户只看到简短结果

| 场景 | 用户反馈 | 页面变化 |
| --- | --- | --- |
| 开始任务成功 | 进入对应任务页面 | 按服务端最新状态更新提醒 |
| 稍后成功 | 已稍后提醒 | 当前卡片移出待处理列表，到期按服务端时间恢复 |
| 忽略成功 | 今日已忽略 | 当天不再显示同一事项 |
| 确认失败 | 操作失败，请重试 | 保留可继续操作的状态 |
| 结果待确认 | 正在确认结果… | 暂时防止重复点击，查询后给最终结果 |
| 后台刷新失败且有缓存 | 更新失败，点击重试 | 保留原内容，用轻量状态标明未更新 |

正常用户页面移除契约版本、接口路径、异常原因、缓存时间等技术说明。开发诊断通过日志记录请求标识、状态码和字段校验位置，不记录令牌、密码或完整业务响应。操作错误与后台刷新错误分开管理，避免点击失败后立即刷新又覆盖原来的提示。

“今天忽略”只改变提醒状态，不代表作业完成；“稍后30分钟”只改变提醒时间，不移动 DDL；“开始任务”不直接标记学习完成。收起提示的数量只统计当前可处理事项，不能把已忽略、延后和进行中的事项都算成新的待处理提醒。

### 2.4 验收

- 首次登录可看到完整引导；再次进入默认收起，注意提示仍清楚可见。
- 收起状态不展示按钮组、理由和技术报错，对话首屏能看到主要内容和输入入口。
- 三个按钮分别成功完成对应动作；合法空字段不再触发“契约不一致”。
- 两台设备的忽略、延后状态一致；连续点击、响应丢失与重试不会重复操作。

## 三、图二、图三：课程与 DDL 跨设备恢复

### 3.1 当前实现为什么会这样

`LearningDataStore` 使用本机 Preferences，按 `userId` 保存课程和 DDL。`AppState.restoreLearningData()` 登录后只恢复这份本地快照。课程名可派生为服务端知识点，但服务端知识点不能还原完整课表、考试日期和作业信息。

因此，同一个账号在另一台设备上可能出现：服务端仍有候选知识点，设备本地却没有原课程和 DDL。这与截图中“有候选知识点、当前任务为 0”的组合相容。

更严重的是，`PlanViewModel.load()` 会先调用 `syncAssignments()`，将本地 DDL 数组上传；`assignment_plan.reconcile()` 按收到的数组重新构造 DDL 任务。新设备的空数组会被解释为完整的空快照。纯内存复现中，原计划 1 项 DDL 任务在同步空数组后变成 0 项，计划版本也发生变化。

### 3.2 P0 止损

1. 立即移除“打开计划页面就上传本机完整 DDL 快照”的路径，计划读取接口不触发业务写入。
2. 明确区分“尚未加载”“已加载且确实为空”“加载失败”，不能统一表示成 `[]`。
3. 过渡期为空快照增加服务端保护，但不能只靠 `if empty then return` 作为最终方案，否则真实删除无法同步。
4. 删除改为带记录 ID 和版本的显式操作；新设备没有本地记录不代表用户删除了服务端数据。

### 3.3 完整同步方案

服务端保存课程和 DDL，设备本地只负责缓存与离线待同步队列。

| 数据 | 服务端保存内容 | 同步规则 |
| --- | --- | --- |
| 课程 | 稳定课程 ID、名称、考试日期、课程安排、账号归属、版本 | 登录恢复；导入和编辑后保存 |
| DDL | 稳定作业 ID、课程关联、标题、截止日期/具体时刻、时区、预计时长、完成状态、版本 | 增改删与完成分别作为显式操作 |
| 当前计划 | 已选择课程、时间预算、已安排/待安排任务、任务状态、版本 | 复用现有计划结构，其他设备直接恢复 |
| 知识点与练习 | 规范知识点 ID、证据、提交、历史 | 继续服务端保存，统一引用课程与知识点 |
| 界面偏好 | 卡片折叠、筛选等 | 按设备和账号保存，不影响业务事实 |

新增课程与作业领域表，通过 Alembic 迁移创建；禁止应用启动时临时建表。账号归属以登录令牌解析结果为准，不信任客户端任意提交的 `userId`。课程 ID、知识点 ID 和账号 ID 均由服务端稳定维护，不能因设备不同重新生成一套身份。

建议 API：`GET /api/v1/learning-data` 读取课程、DDL、数据版本及同步时间；课程和作业分别提供新增、修改、删除接口。写入携带幂等键及预期版本，版本冲突返回 409 后重新拉取，不能静默用最后一次写入覆盖他人的修改。批量导入先预览、再提交，重复导入不产生重复课程和作业。

登录流程改为：恢复服务端身份 → 展示本机缓存或加载态 → 拉取服务端课程和 DDL → 恢复计划与统计 → 合并允许提交的离线操作。同步失败时显示“同步失败，请重试”，不能展示成“没有课程”并引导用户重复导入。缓存按账号和后端环境隔离。

### 3.4 老数据迁移与恢复

- 原设备有本地数据：保留原快照，首次升级后按稳定标识或候选匹配迁移；先核对服务端已有数据，再增量补齐。冲突字段保留双方信息，不能盲目整表覆盖。
- 新设备本地为空：只从服务端恢复，不上传空快照，也不覆盖考试日期或课程设置。
- 曾经被移出计划的 DDL：检查原设备缓存、计划历史和备份；先生成可恢复清单，再确定恢复范围。知识点名称不足以可靠还原完整作业，缺失事实不能编造。
- 删除保留删除标记与版本，防止旧设备重新上线后把已删除记录“复活”。

### 3.5 调整空状态

“没有课程”“同步失败”“已有课程但未选择本次学习安排”“任务都在待安排区”“本轮已完成”分别展示。已有 39 项候选知识点不等于已有当前任务，也不应让用户误以为课程全部丢失。

图二、图三删除“前端不重新计算优先级”等开发说明；主攻课程改为可选择的已导入课程列表，允许搜索，不要求用户手输完全一致的名称。已有服务端课程选择和时间预算时直接恢复。尚未选择时给出“选择本次课程与学习时长”的明确入口，并显示“待安排 X 项”，避免统称“没有可执行任务”。

### 3.6 验收

- A 设备导入课程、考试日期和 DDL，B 设备登录同一服务端 `userId` 后完整恢复；B 查看计划不能减少 A 的任何作业。
- A 编辑、B 刷新可见；B 删除后 A 再上线不会恢复旧记录。
- 两台设备同时修改同一记录会触发冲突处理，不静默覆盖。
- 断网新增、重连、重复提交、卸载后重装均有明确结果；另一账号看不到这些数据。
- 两端核对后端环境和服务端 `userId`，不能只凭相同手机号认定账号相同：当前项目支持一手机号多个账号。

## 四、图四：练习知识点如何整理

### 4.1 改为“先选课程，再看主题，再开练”

推荐结构为“课程 → 主题/章节 → 具体知识点”。例如“数据结构 → 栈 → 基本操作、合法出栈序列”。“排序算法”和“排序算法复杂度”是上下位关系，不应作为完全平级、互相竞争的重复卡片。

默认显示“继续上次练习”和不超过 3 项推荐，再提供“需巩固 / 待复测 / 未测评 / 全部”筛选。完整主题目录可展开或搜索，不再把几十个不同粒度的知识点平铺在首屏。

真正同义的知识点采用规范 ID 与别名，例如同一含义的“二叉树遍历基础”及其别称；“栈的基本操作与特性”和更具体的 Push/Pop 行为不应仅因都带“栈”就合并。跨课程同名知识点也不能直接合并。

导入资料产生的候选名称先映射到规范知识点；无法确定归属的放入“待确认”，不直接制造新的权威目录。迁移只调整引用映射，保留原作答和历史证据，合并时按题目/提交去重，不能简单叠加分数。

### 4.2 用明确状态替代“没记录”和 0 分混排

| 状态 | 卡片示例 | 推荐动作 |
| --- | --- | --- |
| 未测评 | 未测评 · 还没有作答记录 | 开始诊断 |
| 初步结果 | 已答 3 题 · 证据较少 | 再练一组 |
| 需巩固 | 最近有效作答 2/6 正确 | 专项练习 |
| 当前表现较稳定 | 最近有效作答 9/10 正确 | 挑战应用题 |
| 待复测 | 距上次验证已有一段时间 | 做一轮复测 |

未测评的分数应为 `null`，不展示 0 分或空进度条；真实答错导致的 0% 保留，但应写清“本次 0/3”，避免等同于“完全不会”。刚导入资料不能自动获得薄弱判断或掌握分数。

由服务端统一输出测评状态、独立有效作答数、正确数、最近测评时间和证据数量，练习选择器、知识画像、推荐卡片共用。现有 `LearningEvidence.assessed()` 仅从部分直接关联证据与历史推断，应统一兼容逐知识点测评结果及旧数据，避免不同页面得到不同结论。

### 4.3 分数展示建议

短期把“本轮正确率”和“近期练习正确率”放到前面，原有累计掌握度只保留在详情并明确属于旧规则估计。中期用可复算的有效答题统计替代固定增减分：例如每知识点最近 20 道不同题目的无提示首答正确率，并同步显示样本数与覆盖范围。该数值应叫“近期练习正确率”，不能自动包装成能力概率。

重复原题、看过解析后再答、提示辅助作答可记录为巩固活动，但不反复作为独立证据推高掌握结论。数据少时先标“初步结果”；没有最近证据时标“待复测”，不能把旧分数直接清零。旧版和新版结果携带规则版本，原始成绩和历史不回写篡改。

### 4.4 验收

- 同课程知识点有明确层级，同义名称不会重复计入，父主题与具体技能能区分。
- 未练知识点统一显示“未测评”；真实 0% 同时展示题数，不与未测评混淆。
- 同一知识点在练习页、画像页、测评页状态一致。
- 一次提交涉及多个知识点时逐点记录，不仅更新主要知识点；重复提交不重复增加样本。

## 五、图五：测评智能体的职责与实现

### 5.1 当前真实能力

后端的测评能力已经存在：提交练习 → 与答案键比较 → 计算总分与逐知识点正确率 → 更新画像、证据和历史 → 判断是否需要交给规划智能体调整计划。判分和分数更新由确定性代码执行，大模型主要参与题目/解析及部分建议生成。

但前端“测评智能体”目前跳到 `ReviewSummary`。该页面主要展示专注时长、完成任务、任务关联知识点和本地下一步安排，并没有完整呈现上述答题测评结果。因此，入口写着“验证学习是否有效”，实际看到的却像学习打卡汇总。

现有累计掌握度规则如下：

| 本知识点当轮正确率 | 累计掌握度变化 |
| --- | --- |
| 100% | +29 |
| 60% 至不足 100% | +16 |
| 40% 至不足 60% | +4 |
| 低于 40% | -4 |

结果限制在 0—100。例如初始为 0 的知识点即便本轮全对也只变成 29；低于 40% 时又可能仍是 0。这是代码中的演示启发式规则，不是经过验证的学习能力标准，也没有充分体现题数、题目难度、重复练习和长期保持。

此外，当前专注“完成率”还受用户自评影响：自评完成为 100%，部分完成会被限定在 40%—89%。它不能当作测验正确率或学习有效性的依据。

### 5.2 职责重新表达

练习智能体负责“安排练什么、提供练习”；测评智能体负责“依据作答验证目前会多少、哪些还需巩固、下一步做什么”。每次练习提交后自动生成测评结果，测评入口用于查看聚合结果、开始诊断与安排复测，不要求用户额外重复操作。

建议将用户入口改为“学习效果与复盘”，三个层次按需展开：

1. **学习投入**：今日专注分钟、已完成任务、任务完成率。只能说明投入与执行。
2. **练习表现**：本轮正确率、各知识点有效题数、主要错因、与可比基线的变化。
3. **后续验证**：是否需要巩固、是否已有延迟复测证据、下一项任务。

首屏只给一句有证据的结论、一张核心结果卡和一个下一步按钮。无数据时显示“今天还没有学习记录”；只有专注记录时显示“已记录学习投入，完成练习后可验证效果”；有少量答题时显示“已有初步结果，建议继续验证”。不自动宣称“学习已经有效”。

### 5.3 判断标准

“学了多久”“当场答对多少”和“之后还能否独立完成”应分开衡量。长期保持和迁移比即时表现更适合支持学习结论，这与学习/表现区分及延迟测验研究一致。[学习与表现综述](https://bjorklab.psych.ucla.edu/wp-content/uploads/sites/13/2016/11/soderstorm_ra_learningvsperformance.pdf)、[检索练习与延迟保持实验](https://psychnet.wustl.edu/memory/wp-content/uploads/2018/04/Roediger-Karpicke-2006_PsychSci.pdf)。

下表是建议的初版产品规则，题数、时间和阈值需要结合真实课程试测校准；这些具体数值并非上述论文给出的通用标准，也不能据此宣称完成科学能力测量。

| 证据 | 初版判定规则 | 可显示的结论 |
| --- | --- | --- |
| 只有计时/任务打卡 | 有学习记录，没有有效作答 | 已投入学习，效果待验证 |
| 第一次诊断 | 每知识点 3—5 道题，用于建立基线 | 初步结果；不直接认定稳定掌握 |
| 当前表现 | 同知识点至少两轮、累计不少于 8 道不同有效题，包含基础与应用，合计正确率达到 80% | 当前练习表现较稳定 |
| 前后变化 | 同知识点、相近难度、不同题目，满足基本覆盖后比较独立首答结果 | 本次表现提高/暂未改善，注明样本数 |
| 延迟复测 | 24—72 小时后用 3—5 道平行题或应用题无提示复测，达到 80% | 初步保持较好，继续观察 |
| 证据不足或不可比 | 题量少、重复原题、明显难度不一致、答案有争议 | 暂不能判断，建议补充验证 |

若没有有效学习前基线，只能报告当前表现，不能凭空计算“提升多少”。即使前后测改善，也应表达为观察到的变化，不能直接作严格的因果归因。高正确率用户可保留较好表现，不强行要求分数持续上涨才算有效。

推荐示例：“栈的基本操作：本次 4/5 正确；与上次相近难度练习相比表现提高。建议明天用不同题目复测。”不要只给一个没有样本与依据的综合“学习效率分”。

### 5.4 修复 0 分钟、40% 和 0 任务

`getFocusSummary()` 的 `todayMinutes` 按今天过滤，但 `completionRate` 对全部历史专注记录求平均，导致同屏混用不同时间范围。完成任务和待办还涉及服务端计划、本地 `weeklyPlan` 等不同来源，需要一并统一。

修改为服务端按账号、时区和所选周期聚合；默认“今天”，可切“近7天”。同一屏所有指标使用同一周期，并明确“自评完成情况”“任务完成率”和“练习正确率”的不同含义。无分母时显示“—”或“暂无记录”，不展示来源不明的历史百分比。

任务完成率建议定义为“所选周期计划中已完成任务数 / 纳入本周期计划的有效任务数”，排除候选知识点、已取消和仅待安排的任务。计划调整保留版本与时间边界，不能因重排随意改变历史分母。专注记录按会话去重；跨午夜会话按实际学习时间区间拆分，旧记录无法可靠拆分时标注统计限制。

待办与下一步建议统一从服务端当前计划读取；画像和证据统一从测评结果读取，不再用本地旧计划推断。没有下一步安排时给出“选择课程开始诊断/练习”的动作，不展示已经生成下一步计划的暗示。

### 5.5 验收

- 0 条今日记录时显示明确空状态，不混入历史完成率。
- 一轮练习提交后，正确率、逐知识点结果、证据和下一步动作可从测评入口查看，换设备仍一致。
- 只完成计时或自评完成，不能自动提升知识掌握结论。
- 有前测才展示提升；重复原题不作为新的独立测评证据；没有延迟复测不显示长期保持结论。
